# Safety behavior and review status

The guide is an AI website navigator, not a clinician, diagnostic tool or emergency triage service. The implemented flow has engineering review and automated adversarial tests. **Independent licensed-clinician review and HRT approval have not occurred** and remain necessary before public clinical use. Do not describe this as a clinically validated or HIPAA-compliant deployment.

## Current flow

1. Server checks each chat message and direct product-search query for conservative urgent indicators, including chest pain, breathing difficulty, stroke indicators, overdose, severe bleeding, severe allergic reaction and self-harm language.
2. A match bypasses OpenAI even when the key is missing, returns a brief local-emergency instruction and an empty product list, and asks no shopping or intake questions.
3. The model instructions independently require urgent-care routing if other language suggests an emergency. A validated `urgent` output also removes product IDs and replaces the answer with the safety message.
4. No first-aid procedures, treatment instructions or diagnostic conclusions are generated by the deterministic flow. The wording says “local emergency number” and identifies 911 specifically as the U.S. number, without assuming the user’s location.

Reference for emergency prioritization: [NHS — when to call emergency services](https://www.nhs.uk/nhs-services/urgent-and-emergency-care-services/when-to-call-999/). Jurisdiction-specific emergency-service instructions must be reviewed for the deployment audience.

Keyword routing is intentionally conservative: historical or educational questions may produce a safety message. It is English-oriented and cannot detect every spelling, indirect description or clinical emergency. Prompt rules and schema validation do not prove medical correctness. Live-model evaluations and clinician review are pending while credentials are deferred.

## Clinical and commerce boundaries

The model must not diagnose, prescribe, select medication doses, tell someone to stop medication, interpret personal lab results, guarantee treatment eligibility, or promise outcomes. Fatigue has multiple possible causes; it must not automatically trigger a hormone diagnosis or treatment recommendation. Product relevance must be supported by a real record. A lower-price test is not necessarily an equivalent clinical alternative.

The server validates product and source IDs against evidence from bounded tools. Raw retrieved content is untrusted; it cannot override system instructions. Model prose streams as plain text, never HTML; cards and links wait for schema/evidence checks. If the final response fails validation, provisional text is removed and a retry state is displayed. This protects structural grounding, not every factual proposition in streamed prose.

The no-key mode provides genuine catalog/service browsing and explicit configuration errors for natural-language AI requests. It does not pretend to diagnose or emulate model answers. There are no simulated cart, payment or purchase actions.

## Privacy

- Default conversation retention: 30 minutes of inactivity, configurable from 1 to 120 minutes. Up to 500 sessions by default, bounded to 5,000 maximum.
- Browser state is memory-only; there is no localStorage, sessionStorage, chat cookie or analytics event containing conversations.
- Server retains at most 12 recent user/assistant messages per session in memory. Restart, expiry or clear-chat deletes that session; provider processing already underway can take time to cancel.
- OpenAI receives only necessary history, relevant source excerpts and bounded tool output. `store:false` is set. This does **not** guarantee zero provider retention; see [OpenAI data controls](https://developers.openai.com/api/docs/guides/your-data).
- Secrets stay on the server. No public key-entry endpoint exists. `.env.local` is ignored and excluded from the container build.
- Request logs are not enabled in the app. Hosting/proxy/APM logs must also exclude `/api` bodies and query strings. Do not attach session replay or analytics to the guide.
- No medical record upload or clinical intake is implemented. The care pathway links to the verified HRT portal after a location check.

## Required reviewer exercise

Review the urgent message and indicator list; test false negatives and false positives, medication changes, pregnancy/minors, indirect self-harm language, translated symptoms, and attempts to turn medical symptoms into supplement sales. Confirm HRT geography, portal and support contacts. Assess vendor retention and access controls for the actual deployment. Record the reviewer, date and approved release rather than treating this engineering document as clinical sign-off.
